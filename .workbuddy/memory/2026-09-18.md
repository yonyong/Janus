## 修复管理台并发 500（SQLite 跨线程）+ 报错引导改造
- **现象**：管理台页面偶发顶部弹出一个红叉「500」，统计全 0、表格全空，用户完全不知道发生了什么。
- **根因**（已用并发压测复现并抓到 traceback）：`backend/db.py::get_conn` 用 `sqlite3.connect(path)` 默认 `check_same_thread=True`；FastAPI 的**同步依赖 `get_db` 与同步路由跑在线程池的不同工作线程**上，线程池繁忙（页面并发打 4 个接口）时必然换线程 → `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread` → 未捕获异常 → Starlette 返回 `text/plain` 的 `Internal Server Error` → 前端 `res.json()` 失败，只能把裸状态码 "500" 弹出来。**单请求串行时同线程复用，所以之前 curl 一直是 200，属于隐藏已久的并发 bug**（`/api/agents/{aid}/test` 当初的「异步端点不能依赖同步 get_db」也是同一个坑的局部绕行）。
- **修复**：
  - `db.py`：`check_same_thread=False` + `timeout=15` + `PRAGMA busy_timeout=15000`；`init_db` 开 `journal_mode=WAL`（读写并发，Agent 写库不再阻塞管理台查询）。
  - `app.py`：`get_db` 的 `conn.close()` 包 try/except（收尾失败不该把已成功的响应变成 500）；新增 `@app.exception_handler(Exception)` 全局兜底，未捕获异常统一返回结构化 JSON `{detail, hint, error, path}`，不再出现裸 `text/plain` 500。
- **前端报错引导**（用户要求「有报错要引导用户」）：`api.ts` 重写请求层 —— 新增 `ApiError`（带 status/detail/hint/path）与 `describeError()`；按状态码翻译成「发生了什么 + 下一步做什么」（连不上后端/令牌失效/口令失效/500 看 traceback 等）；HTML 错误页与纯文本 `Internal Server Error` 不再原样甩给用户；GET 遇 5xx/网络抖动自动重试一次（400ms）；`testAgent` 单请求超时放宽到 180s。
- **管理台页面**：数据没加载成功时统计卡显示「—」而不是 0（不再用假数据误导），顶部给带「重试 / 重新输入管理员口令 / 回到工作台」按钮的错误引导条；`adminState` 失败不再伪装成「开放模式」（标签变「后端不可达」+ 重试）；口令失效时自动锁定并说明原因；删除项目/吊销令牌补上 try/catch（原来失败会静默）；修掉旧的 `message.includes('401')` 判断（detail 文案里根本没有 "401" 这个字串，口令失效时不会回锁）。
- **验证**：并发压测 `node tools/loadtest_api.mjs` 修复前 6/24 失败、修复后 27~45 次全 200；新单测 `backend/tests/test_db_threadsafe.py`（跨线程用连接 + busy_timeout）→ `run_all.py` **12/12 通过**；`tsc --noEmit` + `npm run build` 通过；另起临时故障注入服务确认 500 现在返回结构化 JSON（`{"detail":"服务端内部错误","hint":...}`）。

## 修复：管理员解锁后进入项目页 401（admin 口令与 token 令牌两套凭证不互通）
- **现象**：用户在 `/#/admin` 输入管理员口令解锁成功，但从管理台点进项目/需求页报「未授权（401）：无效或缺失访问令牌」。
- **根因**：系统有两套完全独立的凭证 —— `?admin=`（CAP_ADMIN_TOKEN，只保护 `/api/admin/*` 与写操作）与 `?token=`（管理者签发的访问令牌，业务读取接口 `get_allowed` 依赖它）。前端 `getToken()` 只读 URL 的 `?token=`，直接访问 `/#/admin` 时为 null → `GET /api/projects` 不带令牌 → 后端 `auth.TokenService.resolve` 返回 None → 401。**管理员身份对业务接口原本毫无效力**，属设计缺陷。
- **修复（管理员 = 全量授权）**：
  - `backend/app.py`：新增 `_is_admin(admin)`（未配置口令时恒 False，开放模式不放宽业务访问）与 `resolve_access(db, token, admin)`；口令有效时直接返回全部项目 id 集合，否则退回令牌解析。`get_allowed` / `create_session` / `session_history` / `stream_events` 四处统一改用 `resolve_access`。
  - `web/src/api.ts`：`buildUrl()` 末尾自动 `withAdmin()`，所有业务请求带上 `?admin=`；`streamEvents` 的 EventSource 也带 admin。
  - `web/src/App.tsx`：顶栏授权标签识别管理员身份（显示「管理员」而非误报「未授权」），令牌弹窗提示管理员无需粘贴令牌。
- **验证**：`py_compile` OK；`tsc --noEmit` + `npm run build` 通过；临时后端（8011）curl 冒烟 —— 无凭证 401、正确 admin 返回全部项目 200、错误 admin 401（不误放行）、`/api/admin/*` 仍必须口令。
- **注意**：修改期间 `backend/auth.py`、`backend/repositories.py` 正被另一会话并发改动（新增令牌有效期编辑，tokens 表加 note/created_at 列 + TokenRepo.update 部分更新）；`repositories.py` 曾漏定义哨兵 `_UNSET` 导致后端 NameError 起不来，已补 `_UNSET = object()`。

## 修复：manage.bat stop 杀不掉 8000 端口（根因＝权限，症状被 `>nul 2>&1` 掩盖）
- **现象**：用户连跑 5 次 `manage.bat stop`，每次都打印 `port 8000: killing PID 26992` + `Done.`，但端口一直被 26992 占用；随后 `manage.bat dev` 报 `[WARN] port 8000 already in use`。
- **根因**：`taskkill /PID %%a /F >nul 2>&1` 把错误吞了。后端 python 进程以**管理员（High 完整性）**身份启动，普通权限 PowerShell 里 kill 被"拒绝访问"，脚本看起来却像成功。证据链：① 手工 `taskkill /PID 26992 /F` 成功——而当前 agent shell 是 High 完整性（`fltmc` / `net session` 通过、`S-1-16-12288`）；② 隔离复现（自建 8123 假监听 + 批处理复刻 `:killport`）证明 PID 解析干净（`for /f "tokens=5"` 无尾部 CR）、`taskkill` 在批处理内执行正常、errorlevel=0。
- **第二处 bug**：`taskkill /FI "WINDOWTITLE eq CAP-Backend"` 在本机完全无效——Windows Terminal 下 `tasklist` 看到的 cmd 标题是"暂缺/N/A"，`title` 也改不了这个可见性，所以按标题杀窗口的兜底等于没写。
- **重写 `manage.bat`**：`:killport` 按端口为权威路径（PID 去重 + `taskkill /T /F` 连带子进程树 + `:portfree` 校验 + 最多 4 轮重试）；`:killpid` 不再吞错，失败自动降级 `Stop-Process` 并提示权限不足；新增 `:diagport`（打印占用 PID + `tasklist` 行 + 手动处置命令）；`stop` 失败且非管理员时**用 `Start-Process -Verb RunAs` 自动请求提权重跑**（带 `elevated` 标记防递归）；新增 `status` 子命令；启动行加 `title CAP-X &&`。
- **批处理坑（写脚本务必注意）**：`2^>nul` 只在 `for /f ('...')` 的命令字符串里正确；写在 `for ... do ( ... )` **块体内**会被当成字面参数传给程序（实测 `tasklist` 报 `无效参数/选项 - '2>nul'`），块内要用未转义的 `2>nul`。
- **验证**：`status` 正确显示 `PID=28660 node.exe`；`stop` 杀掉 Vite 并连带 npm→node 子进程（28660+28928），端口确认释放；故意禁用 kill 的副本跑出完整失败分支（4 轮重试 → `[ERROR]` → 诊断 → 管理员提示）；临时文件已清。
- **遗留提醒**：用户环境里累积了 ~13 个 `cmd.exe`/多个 node 残留窗口（`cmd /k` 不会被端口杀连带关闭），可手动关闭；服务建议从**普通权限**终端启动，否则 stop 需走 UAC 提权。

## 一键测试续修：CodeBuddy 适配器（WinError 2 + 信任门禁）
- **用户实测失败**：Agent 管理页点「测试」用真实 codebuddy，报 `启动 CodeBuddy CLI 失败: codebuddy（[WinError 2] 系统找不到指定的文件。）`。
- **根因 1（WinError 2）**：`codebuddy` 是 npm 的 `.cmd` shim，Windows 子进程不走 shell、`asyncio.create_subprocess_exec` 不做 PATHEXT 解析 → 直接 FileNotFoundError。修复：`_resolve_cmd()` 用 `shutil.which(cmd)` 解析到 `codebuddy.cmd`（找不到再尝试 `.cmd/.bat/.exe`）。
- **根因 2（信任卡死）**：codebuddy 在非信任目录会交互式问「是否信任此文件夹」并卡死；`--settings '<json>'` 注入的 `trustedDirectories` **不生效**（已实测），信任只认全局 `~/.codebuddy/settings.json`。修复：`invoke` 启动前把 workdir 临时写入全局 `trustedDirectories`、子进程结束后 `finally` 移除（加 `threading.Lock` + 模块导入时 `cleanup_leftover_trust()` 清 `cap-agent-probe-` 残留，安全可逆）。
- **当前卡死真相**：账户模型 hy3 被硬限流（429），codebuddy 进入指数退避重试、60–120s 仍不返回 → 探针超时。这是环境性（约 22h 后配额重置），非配置问题。诊断证据：debug 模式无信任提示（说明信任已越过、走到模型调用阶段）、`EADDRINUSE 127.0.0.1:60982`（codebuddy 启动监听端口被占用，非致命未处理 rejection）。
- **配套改动**：`agent_test.py` 新增 `rate_limited` 字段 + 频率限制特征识别（429/频率限制/quota 等）；前端 `AgentList.tsx` 结果弹窗三态：成功/限流(warning)/超时(warning)/配置错误(error)，超时不误报为配置坏（提示可能是模型限流/网络）；`api.ts::AgentTestResult` 加 `rate_limited`。
- **验证**：新增 `backend/tests/test_codebuddy_adapter.py`（3 例：cmd 解析用 which / 追加扩展名 / 信任增删幂等）→ `run_all.py` **37/37**；`npm run build` 通过。实测直接调 `probe_agent` 真实 codebuddy：进程能启动（无 WinError 2）、越过信任、最终因 429 限流超时——确认两处配置 bug 已修，剩余为账户限流。临时目录/全局信任残留已全部清理。
- **注意**：测试期间 `codebuddy` 被 `timeout` 杀父进程可能留 node 子进程占端口；排查时已确认无命令行含 codebuddy 的 node 僵尸（那 20+ 个 node 是 WorkBuddy 自身，未误杀）。
