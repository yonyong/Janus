### 修掉的两个真实问题（都不是测试的问题）
- **阶段被迟到响应覆盖**：`Workbench` 里 `stage` 初值是 `'clarify'`，session 详情与 workflow 两个请求回来后才 setStage。用户刚进工作台就点节点时，晚到的响应会把阶段弹回数据库旧值 → 左栏整个换掉，表现为「点了没反应」。修法：加 `stagePicked` ref，`changeStage` 里置 true，两处加载分支都加 `if (!stagePicked.current)` 守卫。
- **UI 冒烟的两处时序陷阱**：①不能假设进入时是某阶段（数据库阶段由上次操作决定）→ 改为先读进入时阶段、显式切到各节点再断言、跑完还原，避免擅自改演示数据；②读阶段必须等看板数据到位（`stageSummary` 渲染出来）再读，否则读到的是 `'clarify'` 默认值；③进入阶段后立刻点树节点，事件可能落在 React 正重挂载的已脱离元素上 → 展开改成「只在未展开时点、直到可见节点数增长」的幂等重试。经验：**CDP 合成点击前要等数据加载态收敛，否则断言会随竞态随机失败**。

## 追加：修掉「Agent 一键测试必然 30s 超时」——根因是宿主注入的环境变量
- 症状（用户）：Agent 管理页点「一键测试」，30,016ms 超时，事件流为空，提示「多为模型侧限流/网络抖动导致 codebuddy 退避重试」。用户此前已认定是配额问题。
- **根因（与限流无关）**：WorkBuddy 桌面端会往它拉起的子进程注入一整套自己的会话环境变量。后端若从宿主的终端 / 进程树里启动，就把它们原样继承下来、再转发给 `codebuddy` CLI，CLI 于是误判自己跑在宿主网关内部：

## 追加：Agent 一键测试 `info` 字段乱码（GBK 解码）修复
- 症状（用户）：探针已成功返回，但事件流里 `info` 那行是乱码 `ܾʡʡ 'wmic' ...`。
- **根因**：`backend/adapters/codebuddy.py` 把子进程输出 `decode("utf-8","replace")`。codebuddy 的 `.cmd` 启动器在中文 Windows 上会调已废弃的 `wmic`，其报错是 **GBK(CP936)** 编码，被当 UTF-8 解码成乱码。且该 wmic 行是 CLI 启动器的良性噪声（用户 Win 版本已无 wmic），与任务无关。
- **修复**：新增 `_decode()`（UTF-8 优先 → GBK 兜底 → latin-1 兜底 → replace）；`invoke` 里把同时含 `_WMIC_NOISE_MARK`(=「不是内部或外部命令」) 与 `wmic` 的行从 info 事件滤除。前端不用改（已正确渲染 UTF-8 文本）。
- **验证**：`test_codebuddy_adapter.py` 新增 `test_decode_handles_gbk_system_message` / `test_invoke_filters_wmic_noise_from_info`；`run_all.py` **140/140** 通过；`npm run build` 通过。
- **复用要点**：Windows 子进程输出一律走 `_decode()`，别直接 `.decode("utf-8")`；这套 gb2312/gbk 兜底对其他 Windows CLI 适配器同样适用。
